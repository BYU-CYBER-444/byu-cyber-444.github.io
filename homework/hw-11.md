## Description

Configuration drift is one way that hardened systems can become vulnerable over time. This assignment is a **blind diagnosis**: you'll be handed a Rocky Linux 9 VM with two Proxmox snapshots on it - `hw11-baseline` and `hw11-drifted`. The instructor built both. You are not told what was changed between them, how many things changed, or which categories were touched. Your job is to detect the drift yourself, understand what it means from an attacker's perspective, and build tooling that would catch it automatically going forward.

The hardening baseline playbook you need is provided to you (see [Setup](#setup) below); you are not writing a hardening role from scratch here, you're using one as ground truth to detect deviation from it.

---

## Setup

In your proxmox instance there is a VM called `rocky-9-hw-11` with two snapshots already present:

- **`hw11-baseline`** - a clean system with the hardening controls below applied and enforced.
- **`hw11-drifted`** - the same system after an unknown, undisclosed set of configuration changes.

There will also be an lxc container called `hw-11-ansible` that has all the ansible files you will need and are located in `/opt`. Run all `ansible-playbook` commands below from this container.

The playbook enforces hardening across six categories: SSH configuration, service enablement, auditd rules, sysctl kernel parameters, `/etc/shadow` permissions, and `/etc/cron.d` contents.

### Part 1 - Drift Detection (50 pts)

**Step 1 - confirm the baseline is clean.** On `hw11-baseline` snapshot, run:

```bash
ansible-playbook site.yml --check -v | tee hw-11-baseline-output.txt
```

This must show `changed=0`. If it doesn't, something is wrong with your VM assignment - contact the instructor before proceeding, don't debug around it.

**Step 2 - detect drift.** Revert to `hw11-drifted`, then run the same command:

```bash
ansible-playbook site.yml --check -v | tee hw-11-check-mode-output.txt
```

Every task reporting `changed: true` is flagging something that no longer matches baseline. This is your detection signal - not your report. For each `changed` task, go inspect the live system directly (`cat /etc/ssh/sshd_config`, `auditctl -l`, `sysctl <key>`, `stat /etc/shadow`, `cat /etc/cron.d/*`, `systemctl status <service>`, `crontab -l`) and confirm exactly what changed and to what value.

You should expect to find drift across multiple categories, but you are not told the count, and you should not assume it matches any number mentioned elsewhere on this page. Report what you actually find - do not pad your report with categories that came back clean, and do not stop looking just because you've found a plausible-looking handful. Pay particular attention to categories that don't announce themselves loudly (permission bits, cron contents) - `changed=N` in the summary line tells you how many tasks fired, not how many distinct issues exist, since a single category (like auditd rules) can span several tasks.

For **each** drift finding you confirm, document:
- The category (SSH / service / auditd / sysctl / filesystem / cron)
- The exact live-system command you used to confirm it, and its output
- The relevant `changed` task name and diff from the `--check -v` output
- What the value was, and what it should have been per the baseline defaults

You are not remediating the drift - do not re-run `site.yml` without `--check` against `hw11-drifted`. Your job stops at detecting, confirming, and reporting what changed.

### Part 2 - Threat Model for Each Drift Finding (50 pts)

For each distinct drift finding from Part 1, write a threat model entry:

| Drift | MITRE ATT&CK Technique(s) | Attack Scenario | Preconditions for Exploitation | Time to Exploit (estimate) | Detection Opportunity |
|---|---|---|---|---|---|
| *Example (remove before submitting) - Root cron entry in `/etc/cron.d/maintenance` runs `/tmp/.cache/backdoor.sh` every minute; `/tmp/.cache/` is world-writable (`drwxrwxrwt`, mode 1777)* | T1053.003 (Scheduled Task/Job: Cron); T1222.002 (File and Directory Permissions Modification: Linux and Mac File and Directory Permissions Modification) | An internal attacker with unprivileged shell access (e.g., a compromised web app service account) overwrites `/tmp/.cache/backdoor.sh` with a reverse-shell payload. Because the cron entry runs as root every minute, the attacker gets root-level command execution on the next scheduled run with no local privilege-escalation exploit required. | Attacker already has any unprivileged local code-execution foothold; requires no credentials and no additional CVE, only write access to the world-writable path referenced by the cron job. | Under 1 minute (one cron interval) after the payload is dropped. | `auditd` execve record showing `/tmp/.cache/backdoor.sh` spawned by `crond` as `root` with an unexpected outbound network connection; a drift-monitor run flagging a `/etc/cron.d` entry that references a world-writable path. |

**Attack scenario** - describe concretely how an attacker would exploit this specific misconfiguration. Use a realistic attacker model (e.g., external attacker with network access but no credentials, or internal attacker with unprivileged shell access).

**Detection opportunity** - what log entry, network anomaly, or behavioral indicator would be generated if this misconfiguration were actively exploited? Be specific: "Event ID 4624 with Logon Type 3 from an unexpected source IP" is specific; "check logs" is not.

## Tip

{: .tip }
Cron-based persistence is the kind of subtle drift an attacker would introduce: a root cron entry pointing at a script in a world-writable directory. Your drift monitor should check `/etc/cron.d/` against a known-good allowlist and flag any cron entry referencing a world-writable path - don't assume you'll find this one just by reading `sshd_config` and moving on.

Download [hw-11-drift-monitor.yml]({{ site.baseurl }}/homework/assets/hw-11-drift-monitor.yml) as a starting point - it's an Ansible playbook (not the hardening `site.yml` itself) that implements checks across all six hardening categories (SSH config, service enablement, auditd rules, sysctl parameters, `/etc/shadow` permissions, and both `/etc/cron.d` and the root user's own crontab), with timestamped logging to `/var/log/hw-11-drift-monitor.log` and a final task that fails the play - giving `ansible-playbook` a non-zero exit code - whenever drift is found, which is what the systemd unit files below should key off of. The `expected_*` vars at the top of the playbook are the baseline's stated intent, not a verified answer key - confirm each one against your own `--check -v` output and the live system, and correct anything that doesn't match what your playbook actually enforces before you wire it into the systemd timer.

##  Graduate Extension - Graduate Students Only

### Part 4 - Drift Response Playbook (30 pts)

For two of your drift findings, produce a formal **Drift Response Playbook** entry (`hw-11-playbook.md`) following this structure:

| Field | Content |
|---|---|
| Scenario ID | DR-01, DR-02, ... (one per finding) |
| Drift Description | What changed and on what artifact |
| MITRE ATT&CK TTP | Technique ID and name |
| Detection Method | Which check catches it (Ansible check-mode, systemd timer, manual) |
| Triage Steps | Ordered list: what to check first, second, third |
| Containment | Immediate action to prevent further damage (isolate? disable? snapshot?) |
| Eradication | How to restore known-good state (Ansible re-run, restore from backup, rebuild) |
| Verification | How to confirm the system is clean (commands + expected output) |
| Evidence Preservation | What artifacts to capture before remediation and where to store them |
| Escalation Trigger | Criteria that escalate from automatic remediation to human IR |
