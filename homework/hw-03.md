## Description

Production Active Directory environments accumulate stale accounts that become security liabilities - every dormant account is a credential an attacker can leverage without triggering recent-login monitoring. In this assignment you are the analyst handed a discovery report, not the one building the tooling from scratch: you'll run a provided audit script against a real AD environment, interpret its findings, and manually remediate what it flags.

You will be given access to a dedicated AD server for this assignment, seeded with around 200 accounts: a handful of always-excluded service accounts, and a set of accounts that are stale, have an expired password, or both, so your CSV won't look like anyone else's. You do not need to build or provision your own lab domain - work directly against the provided server. Your username on it is your Net ID, and your password is the one emailed to you at the start of the semester.

Connect to the server over **RDP** at `172.19.x.12`, where `x` is the third octet of your own nested subnet (the same one your `pve1`/`pve2`/`pve3` VMs live on). You might see a black screen for a minute or two the first time you use RDP while it is setting up your profile.

### Part 1 - Run the Audit Script & Interpret Results (30 pts)

Download [hw-03-audit.ps1]({{ site.baseurl }}/homework/assets/hw-03-audit.ps1) - this is provided to you, you do not need to write it. It is a **read-only** discovery tool: it queries AD for enabled accounts that are stale and/or have expired passwords, excludes service accounts, and writes a CSV report. It makes no changes to Active Directory.


1. Run the script against the AD server you were given, passing `-Domain` for the DNS domain name of the environment you were assigned (e.g. `-Domain lab.local`) - the script derives its LDAP search base from this. e.g.:

   ```powershell
   .\hw-03-audit.ps1 -Domain lab.local -OutputPath .\reports
   ```

2. Open the resulting `stale-accounts-YYYY-MM-DD.csv` and confirm you understand every row: which threshold(s) each account tripped (`Reason`: `stale` / `expired-password` / `both`), and why the excluded/service accounts were correctly left out.

### Part 2 - Manual Remediation (45 pts)

For each account flagged in the CSV (excluding any the script already excluded), remediate it by hand against the provided AD server:

1. **Disable** the account.
2. **Set the `Description` attribute** to `[DISABLED] Manual review - stale >90d. Disabled by: <your name> on <today's date>` (use the actual `-StaleDays` value the script ran with, not the literal text `90`).
3. **Move the account** to an `OU=Disabled,OU=Users,<your domain's DN>` OU in the domain you were given (e.g. `OU=Disabled,OU=Users,DC=lab,DC=local` for a `lab.local` domain) - create the OU first if it doesn't already exist.
4. **Log every action you take** to `hw-03-remediation-log.txt` - one line per account with a timestamp, the `SamAccountName`, and the action taken. You may do this by hand, with a short PowerShell one-liner, or with ADUC plus a manually-maintained log file; there's no required script for this part, but the log must be real and match what you actually did.

If you hit an error remediating any account (permissions, an already-existing OU, a locked object, etc.), don't just skip it silently - note what happened and how you resolved it in your remediation log.

## Key Concepts

Not a graded part of this assignment - nothing to write or submit here. These explain the reasoning behind what Parts 1-2 have you do, so you understand *why*, not just *how*.

**Why dormant accounts are a risk beyond wasted licenses**

A dormant account is an unmonitored attack surface. Nobody is watching for anomalous behavior on an account nobody expects to be used, so a login on it doesn't trip the usual behavioral baselines the way an active user's odd login would. It also often retains whatever group memberships and permissions it had when it went stale, so if it's compromised, the blast radius is whatever access it accumulated over its lifetime, not some minimal footprint. The clearest real-world example is the Colonial Pipeline ransomware attack in May 2021: DarkSide affiliates got into Colonial's network through a legacy VPN account that was no longer in active use but had never been disabled, had no MFA, and whose password had leaked in a prior, unrelated breach. Because the account wasn't actively used, it fell outside routine access reviews - the exact gap a dormant-account sweep like this one is designed to close. (Source: "Colonial Pipeline hackers gained access via unprotected VPN account," The Stack, June 2021 - https://www.thestack.technology/how-the-colonial-pipeline-hack-happened/)

**Why quarantine (a Disabled OU) instead of deleting immediately**

Moving disabled accounts to a quarantine OU instead of deleting them immediately preserves the ability to reverse a mistake cheaply. Deletion is destructive - SIDs, group memberships, mailbox permissions, and object history are gone, and if the account turns out to belong to someone on leave, a contractor mid-engagement, or an account tied to a legal hold, undoing that is far harder than re-enabling an object sitting untouched in an OU. It also creates a clean audit trail: everything in the OU is visibly "flagged for removal," rather than silently vanishing. A reasonable default is 90 days in `OU=Disabled` before final deletion, giving enough buffer for an account owner or their manager to flag a false positive. Final deletion should require sign-off from someone other than the admin who ran the sweep - typically the security/IT lead or the account owner's manager - so removal isn't a unilateral action by whoever happened to run the script.

**Why `LastLogonDate` alone isn't a reliable staleness signal**

`LastLogonDate` only reflects interactive/Kerberos ticket-granting logons replicated (with a default ~14-day lag) across domain controllers - it doesn't capture service accounts authenticating non-interactively, cached credentials still granting access to file shares, or mailbox/app-password activity via protocols that don't touch `lastLogonTimestamp` the same way. An account can look "dormant" by this field while still actively receiving mail or holding a valid Kerberos ticket from weeks ago. A more reliable signal pairs it with `LastPasswordSet`, sign-in logs from the IdP/Entra ID (if federated), and Exchange/mailbox last-activity timestamps, so a single lagging or narrow signal doesn't drive a deletion decision.

**Why manual remediation doesn't scale**

Remediating by hand at the scale of a handful of accounts is tractable, but a fully manual process breaks down fast past a few dozen: no consistent audit trail of who approved what and when, no protection against an admin fat-fingering the wrong account into quarantine, and no way to catch a "dormant" account that's actually a service account someone forgot to document. At hundreds of accounts, this needs a ticket-per-account workflow with two-person approval, a dry-run/report mode before any account is touched, and idempotent scripting so a partial run can be safely re-run without double-processing accounts already moved.

### Part 3 - LDAP Filter Syntax (25 pts)

Stale-account remediation and directory queries in general both come down to writing correct LDAP filters. Given the abbreviated directory layout below (base DN `dc=corp,dc=lab`):

```
dc=corp,dc=lab
 ou=People
    uid=jsmith   (cn=Jane Smith, memberOf=cn=NetworkAdmins,ou=Groups,dc=corp,dc=lab, userAccountControl=512)
    uid=bvance   (cn=Bob Vance, memberOf=cn=HelpDesk,ou=Groups,dc=corp,dc=lab, userAccountControl=514)
    uid=tlowe    (cn=Tara Lowe, memberOf=cn=NetworkAdmins,ou=Groups,dc=corp,dc=lab, userAccountControl=66050)
 ou=Groups
    cn=NetworkAdmins
    cn=HelpDesk
```

(`userAccountControl` follows the AD convention: `512` = normal enabled account, `514` = disabled account, `66050` = disabled + password never expires.)

Write the exact LDAP search filter string for each of the following:

1. Every enabled account that is a member of `NetworkAdmins`.
2. Every account that is **either** disabled, **or** has password-never-expires set (you'll need the `userAccountControl` bitwise matching rule OID `1.2.840.113556.1.4.803`).
3. A filter that returns `uid=jsmith` **or** `uid=tlowe` by name, using the `|` OR operator explicitly.
